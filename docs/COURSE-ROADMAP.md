# Course roadmap — from first evidence to an independent outpost

Planning baseline: 2026-10-06. Companion to [Learning design](CURRICULUM.md). This is a feasible proposed catalog, not a shipped course or a delivery-date commitment. "Zero to hero" means progressing from supported first steps to independently investigating, building, operating and changing a bounded system; it does not mean production-senior status or a job guarantee.

## Scope and implementation status

There are **86 missions**: **68 core**, **12 optional foundations**, and **6 optional ML**. The core count includes the existing six labs and the four-part final capstone. A learner with the entry capabilities can follow 68 core missions; a programming beginner has an 80-mission route with all foundations; taking both optional branches brings the total to 86. These are catalog counts, not measured completion times. Revisits below reuse a mission with a changed situation and are not extra counted missions.

| Status at this planning baseline | IDs | Count | Meaning |
| --- | --- | --- | --- |
| Implemented labs | I01–I06 | 6 | Existing `signal`, `vault`, `gateway`, `echo`, `ledger`, `recovery` workspaces/checkers; implementation is not proof of fairness, mastery or live tutor quality |
| Next candidate block, unimplemented | D01–D03 | 3 | Small requirements, capacity and contract labs recommended for authoring after the UI and six-mission audit have their own acceptance evidence |
| Remaining proposal, unimplemented | F01–F12, D04–D06, B01–B08, T01–T04, S01–S06, O01–O08, L01–L08, A01–A08, W01–W10, M01–M06, C01–C04 | 77 | No new starters, validators, unlocks, language routing or integrated campaign are supplied by this document |

All 80 additions need implementation and validation. The UI work and fairness audit are separate workstreams; this document does not claim they have passed. Existing acceptance records describe earlier runs, not a fresh run of this catalog. The planning IDs do not rename runtime missions or modify learner progress.

The target learner has substantial iOS experience and some API/SQL/backend experience. Python, deeper database work, quantitative reasoning and operations must be diagnosed separately. New programmers receive the optional entry workshop, with explanations and small guided attempts; they are not expected to infer SQL, Python or terminal skills from a later failure. All player-facing material is English. A lower English band changes scaffolding, not engineering expectations or the correctness contract.

## One evolving system, bounded changes

The campaign follows a delivery outpost: accept supply requests, reserve stock, record movements, notify operators, and reconcile operational facts with reports. Each mission changes one behavior or tests one engineering claim. A chapter exit joins the relevant capabilities; a small script exercise must have a visible consequence in that system rather than an unrelated language puzzle.

The current six labs are separate practice workspaces. Future continuity is an authored feature: preserve an artifact manifest containing contract version, schema/data version, inputs, outputs and verification evidence. Offer an explicit import/copy of the learner's earlier artifact into a new owned workspace, with an untouched checkpoint and a compatibility check. Provide a documented fixture at the same contract version when a prerequisite was challenged elsewhere. Never reset, silently "repair", or overwrite a player's work to start a mission.

Every row is a bounded authoring unit: a narrow ticket, a small fixture, one primary artifact, visible checks, a failure case and a transfer variation. Supply unrelated infrastructure already working. Split a row before implementation if it needs several unrelated new concepts or cannot be resumed at a safe checkpoint. For beginners, guided substeps inside a foundation are expected; the catalog is not a promise that twelve short exercises replace a full introductory programming course. Pilot effort and confusion before assigning player-visible time estimates.

### Runtime and resource policy

- Practice happens in the learner's chosen IDE and terminal. Use Python's standard library and SQLite for entry/core primitives, keeping the existing supported Python baseline until an authored migration justifies changing it. The game itself uses Node/TypeScript; learning its implementation stack is not an entry prerequisite.
- Introduce PostgreSQL when concurrent sessions, isolation and query plans need a real server. Introduce a maintained HTTP/auth library when it reduces unrelated work; pin it and document its behavior at authoring time. Do not teach home-grown cryptography or make rewriting the service into another language a progression requirement.
- Reuse nginx and Compose for the known proxy/network boundary. Add a single disposable Kafka node only at A03, after durable jobs and an outbox establish the problem. A03–A06 teach actual broker behavior; an in-memory imitation cannot satisfy that evidence. A database-backed queue remains a legitimate architecture choice in later designs.
- Prefer local files and SQL before a warehouse service, simple dependency-aware scripts before a scheduler product, and a small CPU model before specialized hardware. Kubernetes, managed cloud, Terraform, Spark/Flink and extra caches are not required core installations. Their problems are discussed where relevant; new tool-specific labs would need separate measured justification and validation.
- Supported targets are desktop macOS and Linux. Linux-specific process behavior uses an explicitly owned disposable environment on macOS; it is not presented as macOS service-manager behavior. Windows, mobile, every browser and every CPU architecture are not implied. Browser verification is headless; the course does not open the owner's IDE, browser or authorization flow unattended.
- Each release must publish measured peak memory/disk, supported versions/architectures, download sizes, port strategy, process count and run timeout. These are not yet measured for future labs. Start with small datasets and one service profile at a time; make a larger load profile opt-in. Performance runs cap requests, duration and data growth and must not target external hosts. An insufficient environment is an environment-blocked result, not learner failure or a simulated pass.
- Create and clean only owned lab resources. No global Docker-context changes, pruning, system trust-store edits, real identity accounts, paid services or GPU requirement. Use synthetic users, local test certificates trusted only by test clients, and fixture secrets. Preserve learner data, pending conversations and existing containers. Quota/auth errors pause model activity without a pay-as-you-go fallback or loss of deterministic practice.

## Prerequisites and ordering

The `Prerequisites` column is the authoritative direct-edge DAG. Comma-separated IDs mean **all** listed capabilities are needed; transitive dependencies are inherited. `—` is an entry node. A foundation dependency can be satisfied either by its lab or a narrow practical challenge demonstrating the same outcome. Record the evidence and supported/independent mode; do not issue synthetic mission completions or deduct existing progress. The current runtime does not yet implement these challenge/skip records.

For an experienced learner, review existing work first, then challenge only uncertain entry capabilities. Do not require twelve remedial exercises before Signal. If a challenge exposes a gap, route to that foundation and let the learner return directly; no whole-course reset. Advanced core missions can also reuse relevant prior evidence after contract/version review, but completion claims remain specific to what was actually demonstrated.

A valid topological sequence is:

```text
F01…F12 (only missing entry capabilities)
I01 I02 I03 I04 I05 I06
D01 D02 D03 D04 D05 D06
B01…B08 → T01…T04 → S01…S06 → O01…O08
L01…L08 → A01…A08 → W01…W10
[M01…M06 optional] → C01…C04
```

This is a convenient reading order, not a chain of unnecessary locks. I03 can run alongside the I02→I04→I05 branch. D02 and D03 are independent after D01. W01 starts after I05 and its foundation capabilities; W04/W05 can run before the messaging chapter. A01 starts after B06 and basic telemetry; Kafka is needed only for its own branch and W09's stream comparison. Follow the table edges when interleaving. **No core mission depends on an M mission.**

The order deliberately introduces contracts and a simple design before more backend machinery, persistence before concurrent writers, test/fault control before delivery automation, access boundaries before multi-user operation, observability before load, durable identity before brokers, and reproducible data before ML. System design returns after measurements and failures can challenge its assumptions. Operations precedes sustained load so that overload is observable and stoppable; it does not require prior mastery of scaling.

### Reading the catalog

Each row provides an objective, a concrete artifact and an executable verification target. The final column contains **Alt** (valid alternative), **Fail** (negative/failure evidence) and **Transfer** (a changed input or situation). Transfer cases are authored under the same visible contract or introduced as a new ticket with an explicit contract delta; they never add hidden requirements after submission.

For planned missions, the checks are a specification for future checkers, not results. Except for I01–I06, no row is runnable yet. For existing missions, the table summarizes the intended public behavior and acceptance direction; the actual source, published brief and fairness-audit evidence must resolve any mismatch. Design review notes are formative wherever a row says `review`; only the stated executable claim receives a deterministic verdict.

These missions serve actual beginners and targeted refreshers. F02–F05 include explained examples followed by a changed practice case, not a blank editor and a reference link. F08–F09 introduce relational vocabulary and SQL from scratch. F10 supplies units, proportions and rates before any capacity formula; M01 later supplies additional mathematical scaffolding for ML.

Language goal: ask a precise question, distinguish "saved" from "running", and report what a command actually showed. Short sentences and optional word banks are sufficient. SQL/Python/math support is technical scaffolding, not an English penalty.

Recommend **D01 → {D02, D03}**, three small independently executable labs using Python standard library, local JSON and supplied loopback HTTP fixtures. F04/F05/F10 are optional just-in-time support for file/test/units gaps; they are not compulsory repeats for the owner. ### D01: requirements with a checkable boundary

Use a short English delivery ticket plus a versioned facts sheet: actors, allowed operation, persistence promise, payload fields/units, latency target and explicit exclusions. The learner creates a structured manifest mapping requirement IDs to observable cases, separating supplied facts, chosen assumptions and questions. An intentionally unresolved choice must list accepted alternatives and their implications in the briefing; a conversational tutor is not required to reveal the answer.

The verifier checks schema, references, compatible units, coverage of every published must-hold fact, and declared case categories. It rejects concrete contradictions, missing required negative cases and an assumption presented as a supplied fact. It accepts different wording, case decomposition and permitted choices. A second ticket changes one fact to expose hardcoded manifests. These checks prove a coherent bounded manifest, not understanding of all real-world requirements or the quality of free-text architecture.

### D02: capacity arithmetic without a magic estimate

Freeze input meanings before authoring: average requests per day, peak multiplier, **mean** request residence time in milliseconds (arrival to completion, including queueing), response bytes, effective written bytes per request, retention days and a stated storage multiplier. Use public equations: average RPS = daily requests / 86,400; peak RPS = average RPS × peak multiplier; estimated average in-flight work during a stable peak interval = peak RPS × mean residence time / 1,000; peak response bytes/s = peak RPS × response bytes; retained bytes = daily requests × written bytes × retention days × storage multiplier. The concurrency estimate assumes stable flow with arrivals matching completions; processing time alone would omit queued requests, and a p95 latency is not a mean. Define which replication/index/overhead allowances the storage multiplier includes. Separate estimates from measurements and publish whether decimal GB or binary GiB is requested. These equations do not prove that a server will sustain the estimated peak.

One public example: 86,400 requests/day, peak factor 4, mean 250 ms, 2,000 response bytes, 500 written bytes, 7 days retention and multiplier 2 gives 1 average RPS, 4 peak RPS, 1 estimated in-flight request, 8,000 response bytes/s and 604,800,000 retained bytes. Supply that explanation; assess the general calculator on additional values. Publish rounding/tolerance, finite nonnegative ranges, allowed retention values, zero-traffic behavior and rejection of missing/negative/non-finite inputs. Decimal/rational or correctly bounded floating-point implementations may all pass. Never require a chosen variable name, one formula layout or an exact English explanation. Operational load measurements revisit these assumptions at L01/L08.

### D03: test a contract, including a plausible impostor

Supply an isolated fixture service and CLI entry contract for a probe, not a reference implementation to copy. Publish required request method/path/query behavior, content type/body fields, success/error behavior and a bounded side-effect observation. The probe emits per-requirement results. Run it against at least two structurally different conforming fixture implementations and several faulty ones: status-only success, wrong payload, unknown route accepted, duplicate effect and unavailable endpoint. Conforming fixtures must pass, actual violations must fail, and environment unavailability must be distinguished from an assertion mismatch.

Vary payloads, IDs and ports while keeping the published rules fixed. Accept alternate assertion algorithms and harmless serialization differences. Fresh fixtures and state inspection prevent an always-pass probe or a canned expected response from appearing successful. The reference oracle should be derived independently of the learner/reference probe, with an explicit requirement-to-case matrix.

## Evaluation boundaries

Keep four records distinct:

| Record | What can be established | What it cannot establish |
| --- | --- | --- |
| Executable technical evidence | Contract version, actual artifact/input, real requests/DB/file effects, pass/fail per public rule, environment and failure logs | Unmeasured scale, all possible bugs, production readiness or overall professional grade |
| Design submission | Diagram/ADR/assumptions provided; structured references and arithmetic consistent; a stated probe reproduced | A schema-valid design being the right architecture, sound prose reasoning or exhaustive threat coverage |
| Formative review | Specific questions, contradictions to investigate, justified alternatives and reviewer identity/limits | A model's confidence, praise or agreement becoming a deterministic architecture verdict |
| Transfer and communication | A changed task actually solved, support used and observed English communication | A canned repeated answer proving independence, a language exam score or spoken ability |

Free-text architecture has no unique reference answer. Review against the visible constraints, ownership, paths, failure handling, estimates, trade-offs and reversibility, accepting multiple coherent designs. Ask for an experiment on the least certain claim. If a critic identifies a violation, tie it to a published requirement and reproduce it where possible. Rejecting a specific contract violation is legitimate; rejecting an architecture merely because it differs from the author's diagram is not.

For design-heavy missions, `submitted`, `probe verified` and `review pending/reviewed` must remain distinguishable. The model cannot write progression state, override a failed deterministic check or revoke a passed outcome through free-text opinion. A qualified human review can add evidence when available, but the owner is not responsible for being the expert who validates the course. Without independent review, preserve the limitation; do not silently promote rubric completeness into technical mastery.

Performance/ML checks need declared tolerances, workload and sampling procedures. Synthetic data, deterministic fault clocks and controlled adapters are useful test tools and must be labeled as such. They do not establish live model-assessment accuracy, real provider authorization, production traffic capacity or real-world predictive value. No live tutor evaluation or new mission execution was performed in preparing this roadmap.

## Authoring and release gates

Every generated or manually authored mission must pass this gate before it becomes available. Generation is a way to draft content, not evidence that the content is correct. Review and tooling effort have not been measured; do not invent a production throughput or total course schedule.

1. **Capability and scope:** one primary outcome, direct prerequisites, bounded inputs/data and explicit exclusions. A beginner path includes missing concepts; an experienced path offers a specific challenge. Define artifact and transfer evidence before writing the solution.
2. **Contract traceability:** map every blocking check to a visible requirement. Publish input grammar, units, error behavior, duplicate/conflict semantics, ordering, persistence and the failure model where applicable. Separate deliberate starter defects, optional theory and stretch goals. Hidden fixtures may vary examples, not rules.
3. **Independent oracle:** derive expected results from the contract and relevant authoritative documentation, not by copying the reference solution's output. Use hand-computed tiny cases, persisted-state inspection and a second independently derived approach for critical invariants. A second model sharing the same assumptions is not enough.
4. **Fairness and adversarial checks:** intended starter fails; at least two materially different valid approaches pass unless a justified technique-specific objective forbids alternatives. Invalid/degenerate approaches fail: always-pass checks, canned fixtures, silent data loss, swallowed exceptions, source-pattern hacks and state stored only until restart. Do not require file layout or algorithm beyond an explicitly taught interface.
5. **State, failure and transfer:** replay, restart, interrupted execution, malformed/late input and unrelated sentinel data are covered when relevant. Fresh values catch hardcoding. Tests distinguish infrastructure unavailable from wrong learner behavior. Preserve artifacts and explain the failing requirement, observed result and relevant evidence.
6. **Pedagogical read-through:** inspect story, brief, starter, learning text, commands, hints and verifier together. Have an independent reader attempt the task without reference solution/hidden tests. If no such attempt has occurred, report authoring evidence but do not claim learner clarity validated. Hints progress from investigation to concept to concrete help without imposing one algorithm.
7. **Real execution and platform evidence:** use real HTTP/SQL/files/processes for the claimed boundary, Node tests for game integration and headless Playwright for the learner loop. Run build, tests and E2E after implementation. Record exact runtime/OS/architecture; test macOS and Linux support instead of inferring it. Pin dependencies and check official docs again for actual selected versions. Platform simulations remain labeled.
8. **Progress and language separation:** verify idempotent technical awards, resume/reload, optional post-brief, alternative wording and preserved pending messages under quota/auth/offline errors. Tutor output cannot complete a broken lab. Technical success cannot depend on a paid/model response, arbitrary phrase or language level.
9. **Resource and ownership gate:** publish measured requirements; use only owned workspaces, processes, ports, images/volumes and synthetic secrets. Check cleanup does not touch existing resources. A missing dependency yields setup guidance without resetting work. No GUI or real authorization is initiated unattended.
10. **Release record:** preserve brief/checker/fixture versions, RED/GREEN/alternative/negative evidence, known limits, sources and prerequisite links. Changing a requirement versions the contract and offers a safe migration; it does not retroactively erase learner completion. Release a small block, observe confusion and revise before expanding.
